# Общий стандарт программирования (CODING-STANDARD.md)

Единый стандарт для 15 проектов: **Ai-Business, Ai-Purse, Aila, Al-Navi, Barter, Diary,
DuoPulse, LeCards, LingoHub, LingoTune, NovaGrid, R-Admin, Scheduler, Sontse, Synchro**.

Канонический источник — `D:\Scheduler\CODING-STANDARD.md` (репозиторий диспетчера задач).
Копия лежит в корне каждого проекта; при расхождении верен канонический файл. Изменения
стандарта идут задачей диспетчера (карточкой) с согласованием у хозяина, после чего копия
рассылается во все проекты одной правкой.

> Зачем: все проекты делаются одними руками (хозяин + AI-ассистенты под управлением
> диспетчера D:\Scheduler). Единые правила дают предсказуемый код, безопасные изменения,
> проверяемый результат и накопление опыта вместо его потери.

## 1. Принципы кода

1. **Работает — не трогай без причины.** Рефакторинг — отдельной задачей, не попутно.
2. **KISS** — простое решение лучше умного. **YAGNI** — не делаем впрок. **DRY** —
   копипаста логики это сигнал вынести общее.
3. **Явное лучше неявного**: говорящие имена, никакого «магического» поведения; код
   читает тот, кто его не писал.
4. **Маленькие шаги**: одно изменение = одна задача = один коммит — легко проверить
   и откатить.
5. **Единый источник правды**: константы, статусы, справочники — в одном месте,
   остальное только импортирует, дублей определений нет.
6. **Идемпотентность, где уместно**: повторный запуск скрипта/демона не ломает состояние.
7. **Fail loud**: ошибка — внятное сообщение и запись в лог, а не тихий `results[0]`.

## 2. Жизненный цикл задачи (через диспетчер)

1. Задача приходит карточкой из TASKS.txt диспетчера (или задаётся хозяином в чате Aila).
2. Прочитать карточку целиком → `status: in_progress` → **backup.bat** (см. §3) → выполнить.
3. Существенные шаги и решения — в «Журнал» карточки (дата — что сделано).
4. Каждый критерий готовности проверяется по факту, выполненные отмечаются `[x]`.
5. Отчёт — записью в `CHANGELOG.md` в корне проекта: `## <дата время> — <заголовок>`
   плюс обязательные строки «Начало работы» и «Окончание работы» (дата и время), что
   сделано / как проверено / коммит. Без записи задача не принимается. В `promt.txt`
   проекты диспетчера больше не пишут — файл заморожен как архив (карточка
   scheduler-035).
6. Коммит и push в том же сеансе (см. §8). Карточка → `done`, либо `blocked` с причиной
   в журнале.

## 3. Безопасность данных

- **Перед серьёзными изменениями — копия проекта через `backup.bat`** (двойной клик;
  архив в `backups/`, хранятся последние, старые ротационно удаляются). Серьёзное —
  правки кода/БД/конфигов и всё, что затрагивает живые данные; добавление док-файла
  серьёзным не считается.
- **Секреты — только в `.env`** (он в .gitignore, никогда в код и коммиты): ключи API,
  пароли БД, токены ботов.
- **БД**: изменение схемы — миграциями; автогенерированную миграцию вычитывать руками и
  вычищать лишнее. Боевые таблицы не TRUNCATE'ить без явного указания в задаче. Скрипты
  данных (seed/fix) — по умолчанию dry-run, `--apply/--force` — осознанно.
- **Необратимые операции** (удаление, перезапись, рассылка наружу) — только с уверенностью
  в основании; сомневаешься — спросить хозяина (чат Aila).

## 4. Тестирование и проверка

- **После каждого изменения кода — тесты проекта** (если они есть): обязательный прогон,
  результат — в отчёте. Зелёные все; красные чинятся, иначе задача не закрывается.
- **Исправление бага = тест на регресс** (минимум повторяющий сценарий), чтобы дефект
  не вернулся.
- Новая нетривиальная логика сопровождается тестом, если проект уже тестовый.
- **Сборки приложений (apk и др.) — всегда в `builds/`** с версией и типом в имени:
  `builds/<проект>-v1.2.3-debug.apk`, `…-release.apk`. Артефакты сборок не коммитятся
  (в .gitignore), если задача прямо не требует иного.
- Тестов в проекте нет — проверка ручная по шагам, и она описывается в отчёте.

## 5. Чистота репозитория и временные файлы

- **Временные файлы после работы удалять**, если дальше не нужны: `_tmp/`, черновики,
  логи отладки, одноразовые скачанные данные, staging-папки бэкапов.
- Рантайм-артефакты (логи, кэши, стейт, `test-results/`) — в `.gitignore`, не в коммитах.
- В коммит не попадает мусор: сборки, медиа-библиотеки, `.env`, служебные папки
  инструментов.
- Нашли забытый мусор (вида `_tmp/`, `_backup_temp/`) — несерьёзно: почистить сразу;
  серьёзно/объёмно — карточка на разбор.

## 6. Обнаружили проблему

- **Несерьёзная** (опечатка, мелкий баг, мусорный файл, битая ссылка в доке) —
  устраняем сразу в рамках текущей задачи, фиксируем в журнале и отчёте.
- **Серьёзная** (ломает логику, требует времени/рисков, вне рамок задачи) — отдельная
  карточка `CARDS/NNN-…md` (`status: todo`) с конкретными критериями готовности;
  попутно не лезем.
- Дефекты не замалчиваются: даже «починено на месте» честно описывается — что было,
  почему, как исправлено.

## 7. Самообучающаяся система (петля опыта)

Все проекты — одна самообучающаяся система: ассистент под управлением диспетчера
**размышляет и анализирует**, а не только исполняет.

- **После каждой задачи** — короткий вывод: что сработало, что нет, какая грабля. Грабли
  и рецепты — в AGENTS.md проекта (раздел правил/грабель), чтобы следующий сеанс не
  наступал на них повторно.
- **Анализ инцидентов**: сбой/аномалия → причина → фикс → защита от повтора (тест или
  guard), а не только латание симптома.
- **Креативные предложения**: идеи улучшений и новшеств не внедряются молча — предлагаем
  хозяину **на согласование в чат Aila** (там и общаемся): суть, выгоды, риски, оценка
  усилий. Согласовано → карточка → реализация.
- **Накопленные нормы** живут в этом файле и в `RULES.txt` диспетчера; противоречия
  между проектами — сигнал обновить стандарт.

## 8. Git

- Коммиты с осмысленными сообщениями (что и почему; для карточек — «(карточка NNN)»).
- **Коммит → push сразу в том же сеансе** (`git push origin main`), заканчивать с
  `ahead 0`: бэкап-zip'ы не содержат `.git`, непушеное живёт только на локальном диске.
- Работаем в `main` (репозитории персональные); эксперименты — отдельной веткой.
- Не коммитим чужие незавершённые правки: `git status` перед коммитом, добавляем только
  файлы своей задачи.

## 9. Документация

- `AGENTS.md` — главный справочник проекта для AI-ассистентов: карта кода, стек, правила
  и грабли; актуализируется при изменении того, что описывает.
- `README.md` — обзор для человека (быстрый старт). `ROADMAP.md` — планы и этапы,
  корректируется задачей. История изменений — **`CHANGELOG.md` в корне каждого
  проекта, единое место всей отчётности**: каждая правка дополняет его записью
  (дата и время начала и окончания работы, что сделано, как проверено, коммит)
  в конец файла; файла нет — создаётся (правило введено карточкой scheduler-033,
  формат усилен карточкой scheduler-035). `promt.txt` заморожен как архив и
  не пополняется — диспетчер и сессии пишут только в CHANGELOG.md.
- Обновление документации — часть задачи, а не «потом»: изменили поведение — доку
  обновили тем же коммитом.

## 10. Стиль кода по языкам

Общее для всех языков: говорящие имена (латиницей, регистр по конвенции языка), функция
делает одну вещь, ранний return вместо пирамиды вложенности, комментарии — только для
неочевидных ограничений и «почему», а не «что»; мёртвый код и закомментированные блоки
удаляются (git помнит всё).

| Язык | Правила |
|---|---|
| **Python** | PEP 8; f-строки; type hints в новых модулях; после правки сервиса — `python -c "import py_compile; py_compile.compile('<файл>', doraise=True)"`; standalone-тесты запускаются напрямую `python <test>.py` |
| **JS/TS/Node** | `const` по умолчанию; async/await без глубокой вложенности колбэков; модульная система как в проекте (ESM `.mjs` / CJS `.cjs` — не смешивать); в TS — строгие типы, `any` только как осознанная заглушка |
| **Svelte / фронт** | логика в компоненте минимальная, повторное — в общих модулях; строки UI — через словарь/i18n проекта |
| **Kotlin (Android)** | официальные конвенции Kotlin; `!!` только с обоснованием; UI-строки в ресурсах; apk собираем в `builds/` с версией и типом сборки |
| **Dart/Flutter** | Effective Dart; `final`/`const` где возможно; `flutter analyze` без замечаний перед коммитом |
| **Rust (Tauri)** | `cargo fmt`; `cargo clippy` без предупреждений; `Result` вместо паник в библиотечном коде |
| **C# (.NET)** | конвенции .NET naming; async до конца (без `.Wait()`/`.Result`); null-безопасность |
| **1С** | русские имена в стиле конфигурации; процедуры короче экрана; записи/проведения — транзакционно |

Таблица — ориентир; специфика и запуски конкретного проекта — в его `AGENTS.md`.

## 11. Чек-лист перед закрытием задачи

- [ ] Задача выполнена полностью, как сформулирована
- [ ] Тесты / сборка / ручная проверка прогнаны, результат описан в отчёте
- [ ] Временные файлы удалены, в коммите только файлы задачи
- [ ] Отчёт дописан в `CHANGELOG.md` (дата-время начала и окончания, что сделано, как проверено, коммит)
- [ ] Коммит запушен, `ahead 0`
- [ ] Документация (AGENTS / README / ROADMAP) актуальна
- [ ] Найденные проблемы устранены или оформлены карточками
- [ ] Выводы и грабли зафиксированы; предложения новшеств — в чат Aila
